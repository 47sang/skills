# review-and-iterate

实现完成后，对当前分支的变更进行「三路审查 → 自动修复 → 迭代验证」的闭环工作流。

## 概述

本技能在 `implement-specs` 完成后手动触发，对当前工作目录所属分支的变更（默认对比当前分支基线）进行三路并发审查：

1. **规范合规审查**：对照 specs/PRODUCT.md + TECH.md，逐条核验实现是否与规格一致
2. **AI 编码陷阱审查**：分发审查子代理，检查 AI 生成代码的常见缺陷（硬编码、遗漏边界、错误假设、违反项目约定等）
3. **工程规范审查**：分发审查子代理，检查 ruff / 类型标注 / docstring / 测试覆盖等工程规范

审查结果写入清单文档，自动派发子代理修复，修复后由另一子代理验证，多轮迭代直至通过或达到上限。

> **⚠️ 不可变约束**：`specs/<spec路径>/PRODUCT.md` 和 `TECH.md` 为需求的唯一权威定义（SSOT），**本技能执行过程中不得修改规格文档和技术文档**。迭代仅作用于代码实现，规格文档的任何变更必须由用户在迭代之外单独确认后进行。

## 触发方式

```bash
/review-and-iterate [spec路径]
```

| 参数 | 说明 | 示例 |
|------|------|------|
| `spec路径` | 规格目录路径，选填。不填时自动提取 specs/ 下编号最大的目录 | `specs/07-XX功能/` |

> **默认行为**：不传 `spec路径` 时，读取 `specs/` 目录，按编号排序取最大者作为目标规格。

### Phase 1：初始化

1. 读取 `specs/<spec路径>/PRODUCT.md` 和 `TECH.md`
2. 读取 `CLAUDE.md` 中相关约束（技术栈、工程规范、已锁定决策）
3. 计算变更 diff 范围：
   ```bash
   BASE_SHA=$(git rev-parse HEAD)
   HEAD_SHA=$(git rev-parse HEAD)
   ```
   当前分支即为对比基线，HEAD_SHA 即当前工作树状态。
4. 确定迭代参数：
   - 最大迭代轮次：**4 轮**（默认）
   - 审查维度：三路并发（规范合规 / AI 编码陷阱 / 工程规范）
5. 加载或创建清单文档（见「清单文档管理」）

### Phase 2：三路并发审查

三路审查**并发执行**，各自独立产出审查结果并写入指定路径的 markdown 文件。

```

```

- `PRODUCT.md` 中每条用户可见行为是否实现
- `TECH.md` 中每项架构 / 顺序 / 实现形状约定是否遵守
- 规格中的接口定义、数据结构、协议格式是否一致
- 规格中的一期 / 二期边界是否遵守（一期功能不可提前实现）

输出：问题列表（每项含：规格依据、当前实现、偏差描述、严重程度）

### Phase 3：汇总审查结果

三路审查完成后，读取三份 markdown 文件，汇总审查结果：

1. 读取 `REVIEW-<轮次>-A.md`、`REVIEW-<轮次>-B.md`、`REVIEW-<轮次>-C.md`
2. 合并问题列表，按严重程度分级

| 严重程度 | 说明 | 处理优先级 |
|----------|------|-----------|
| **严重** | 功能错误、规范偏离、安全风险 | 立即修复 |
| **中** | 边界遗漏、异常处理不完整 | 立即修复 |
| **低** | 代码风格、注释不完整 | 记录待处理 |

3. 将汇总结果写入**单轮清单文档** `REVIEW-<轮次>.md`

### Phase 3.5：判断分诊（判断门，2026-09-21 起）

汇总完成后、派发修复前，把合并后的问题清单逐条交给判断门分诊（specs/19 §3.6），**路由结论优先于严重程度标签**：

1. 把本轮全部问题整理为 JSON 数组（每项含 `id`、`title`、`detail`（问题 + 当前实现）、`evidence`（代码位置与证据）），写入临时文件（如 `/tmp/review-findings-<轮次>.json`）
2. 运行分诊命令：

   ```bash
   python3 scripts/hooks/jev_gate.py findings --file /tmp/review-findings-<轮次>.json --project Seedream-Images
   ```

3. 按路由结果分派，不做自由裁量：
   - `auto_fix`：进入 Phase 4 的修复任务清单（真缺陷且严重度达标）
   - `register`：写入清单文档问题清单并标记 `[x] 登记不修`（严重/中但判定不阻塞的也照此登记，附判断门理由），不派修复
   - `escalate`：标记 `[?]` 需人工介入，列入最终报告
4. 判断门不可用（网络 / 缺密钥）时回退旧规则（严重 + 中修复、低登记），并在最终报告注明「判断门未参与本轮分诊」

### Phase 4：派发修复子代理

1. 读取当前轮次的单轮清单文档 `REVIEW-<轮次>.md`
2. 将清单中的**严重 + 中**问题汇总为修复任务描述
3. 派发**单个修复子代理**，按问题顺序逐一修复
4. 修复子代理完成后，重新运行相关验证（`make check` = Pyright 类型检查 + pytest）

修复子代理 prompt 要点：
- 读取 `REVIEW-<轮次>.md` 中的问题清单
- 逐项修复严重 + 中问题
- **🔒 不得修改 `PRODUCT.md` 和 `TECH.md` 规格文档**
- 修复后运行验证命令确认不破坏现有功能
- 修复结果回写到清单文档的「修复记录」表格

### Phase 5：派发验证子代理

1. 派发**独立的验证子代理**，检查修复子代理的修复结果
2. 验证子代理读取 `REVIEW-<轮次>.md`，逐项检查：
   - 问题是否真正修复（重新阅读修改后的代码确认）
   - 修复是否引入了新问题
   - 相关测试是否通过
3. 输出验证报告，回写清单文档的修复状态标记

验证子代理 prompt 要点：
- 读取清单中每个标记为「已修复」的问题
- 对每个修复项，读取修改后的代码，确认问题已解决
- **🔒 不得修改 `PRODUCT.md` 和 `TECH.md` 规格文档**
- 运行相关测试确认没有引入回归
- 将验证结果标记到清单：`[x]` 已修复 / `[!]` 未修复 / `[?]` 需人工介入

### Phase 6：回写清单文档

将验证结果回写到单轮清单文档 `REVIEW-<轮次>.md`：

| 状态 | 标记 | 说明 |
|------|------|------|
| **已修复** | `[x]` | 问题已修复，附修复说明和验证结果 |
| **未修复** | `[!]` | 问题未修复，附未修复原因 |
| **需人工介入** | `[?]` | 需用户确认后修复，附原因 |

### Phase 7：迭代判断

```
还有未修复的严重/中问题？
  AND 未达到最大迭代次数？
    │
    ├─ 是 → 进入下一轮
    │         │
    │         ├─ 当前轮次 >= 2？
    │         │   AND 存在前序清单文档？
    │         │     │
    │         │     ├─ 是 → 合并所有前序清单 → REVIEW-MASTER.md
    │         │     │        检查反复出现/反复修改不了的问题 → 标记需人工介入
    │         │     │        回到 Phase 2（用总清单做比对）
    │         │     │
    │         │     └─ 否 → 直接回到 Phase 2
    │         │
    │         └─ 当前轮次 = 最大轮次？
    │             │
    │             ├─ 是 → 生成最终报告 → 结束
    │             │
    │             └─ 否 → 回到 Phase 2
    │
    └─ 否 → 生成最终报告 → 结束
```

### Phase 8：生成最终报告

当达到最大迭代次数或所有严重 / 中问题全部修复时，生成最终报告：

```
specs/<spec路径>/REVIEW-FINAL.md
```

## 执行约束

1. **对比基线**：默认与当前分支 HEAD 对比，无需额外说明基线配置
2. **最大迭代次数**：3 轮（默认），达到后强制生成最终报告
3. **修复范围**：以判断门路由为准（Phase 3.5）——`auto_fix` 修复、`register` 登记不修、`escalate` 升级人工；判断门不可用时回退旧规则（严重 + 中修复、低登记）
4. **人工介入**：反复出现 2 次以上或修复后复现的问题，自动标记需人工介入
5. **文档持久化**：所有清单文档写入 `specs/<spec路径>/` 目录
6. **中间产物保留**：三路审查的原始输出（-A / -B / -C.md）作为审计痕迹保留
7. **🔒 规格文档不可修改**：`PRODUCT.md` 和 `TECH.md` 为需求 SSOT，**本技能全流程中不得修改**。迭代仅作用于代码。如发现规格与实现存在无法调和的矛盾，必须在清单文档中标记为「需人工介入」，由用户确认是否修订规格后再执行
8. **🤖 判断门分诊**（2026-09-21 起）：问题路由以判断门结论为准，见 Phase 3.5；阈值不在技能内自定，统一在 `scripts/hooks/jev_config.json`（改阈值须经用户确认）
